M3U 파일에는 기술적이라는 평판이 따라다니지만, 그럴 자격은 없습니다. 아직도
매일 쓰이는 형식 가운데 가장 단순한 축에 듭니다. 이름의 목록, 주소의 목록,
그리고 몇 가지 선택적인 메모. 텍스트 편집기로 읽을 수 있고, 한 번 읽고 나면
플레이어의 많은 동작이 더는 제멋대로로 보이지 않습니다.

아래는 완전하게 동작하는 재생목록입니다. 채널 둘, 생략 없이.

```
#EXTM3U url-tvg="http://example.com/guide.xml"
#EXTINF:-1 tvg-id="one.example" tvg-name="Channel One" tvg-logo="http://example.com/one.png" group-title="뉴스",채널 하나
http://example.com/live/one.ts
#EXTINF:-1 tvg-id="two.example" tvg-name="Channel Two" group-title="스포츠",채널 둘
http://example.com/live/two.ts
```

형식은 이것이 전부입니다. 아래는 저 다섯 줄을 둘러보는 이야기입니다.

## 머리글

```
#EXTM3U
```

첫 줄은 정확히 이래야 하며, 그 유일한 임무는 "지금부터 나오는 것은 확장 M3U
다"라고 알리는 것입니다. 이 줄이 없는 파일도 불러와질 수는 있지만, 플레이어가
뒤이어 오는 설명 줄을 기대할 이유는 없어집니다.

머리글은 재생목록이 자기 편성표를 가리킬 수 있는 자리이기도 합니다.

```
#EXTM3U url-tvg="http://example.com/guide.xml"
```

`url-tvg`(같은 뜻인 `x-tvg-url`도 됩니다)는 XMLTV 파일을 지목합니다.
[자기 일정표를 가진 별개의 문서](/ko/blog/epg-편성표-이해하기/)로, 지금 무엇이 방송 중이고
다음은 무엇인지를 공급합니다. 재생목록이 이것을 지녔는데도 편성표가 나타나지
않는다면, 적어도 두 파일 중 어느 쪽을 탓해야 할지는 정해집니다.

## 설명 줄

```
#EXTINF:-1 tvg-id="one.example" tvg-name="Channel One" group-title="뉴스",채널 하나
```

`#EXTINF`은 항목 하나를 여는 줄입니다. 세 부분으로 나눠 읽으십시오.

**숫자.** 콜론 바로 뒤에는 초 단위의 길이가 옵니다. 생방송에서는 `-1`, 즉
"정해진 길이 없음"입니다. 방송은 그냥 계속되니까요. 영화라면 실제 숫자가 들어
있을 수도 있습니다.

**속성.** 선택적인 `key="value"` 쌍입니다. 중요한 것들:

- **`tvg-id`** — 이 채널을 XMLTV 편성표의 프로그램과 이어 주는 식별자입니다.
  편성표는 불러와지는데 아무것도 안 보이는 가장 흔한 원인이 바로 이것입니다.
  재생목록과 편성표가 식별자에서 어긋나면 아무것도 맞물리지 않습니다.
- **`tvg-name`** — 편성표와 맞추기 위한 채널 이름으로, 화면에 뜨는 이름과 늘
  같지는 않습니다.
- **`tvg-logo`** — 채널 로고의 주소입니다. 네트워크로 받아 오는 이미지이며
  채널마다 하나씩이라, 큰 목록이 처음에 완성된 모습이 되기까지 잠시 걸리는
  이유가 여기 있습니다.
- **`group-title`** — 채널이 분류되는 범주입니다. 플레이어에서 스크롤하며
  지나치는 모든 범주 제목은 여기에, 사업자의 손으로, 채널 하나하나마다 입력된
  것입니다. [범주를 직접 길들일 가치가
  있는](/ko/blog/큰-재생목록-정리하기/) 이유이기도 합니다.

**표시 이름.** 쉼표 뒤부터 줄 끝까지가 실제로 보이는 이름입니다. 따옴표 없는
평범한 글자라서, 채널 이름 안에 들어간 쉼표는 이 형식의 진짜 함정입니다.

## 주소

```
http://example.com/live/one.ts
```

`#EXTINF` 바로 다음 줄이 영상이 사는 곳입니다. 재생 시점에 네트워크에 닿는
파일 내 유일한 줄이며,
[스트림이 어떻게 동작할지](/ko/blog/스트리밍-프로토콜-이해하기/)도 이 줄이
결정합니다. `.m3u8` 주소는 조각으로 전달되는 HLS 스트림이고, `.ts` 주소는
끊김 없이 이어지는 전송 스트림입니다.

여기서 쓸모 있는 결론이 둘 나옵니다. 첫째, 설명 줄만 있고 주소가 없는 항목은
보이지 않습니다. 재생할 것이 없기 때문입니다. 둘째, 목록은 완벽히 불러와지는데
모든 채널이 실패한다면, 그것은 이름은 멀쩡하고 주소가 죽은 재생목록입니다.
[플레이어가 아니라 사업자 쪽의 문제](/ko/blog/iptv-플레이어가-하는-일/)인 셈이죠.

## 거기에 없는 것

이 형식이 담지 못하는 것 또한 그만큼 많은 것을 알려 줍니다.

- **영상은 없습니다.** 채널 사만 개짜리 재생목록도 몇 메가바이트의 글자일
  뿐입니다. 그중 한 프레임도 그림이 아닙니다.
- **로그인은 없습니다.** 인증이 필요한 경우 그것은 대개 주소 자체에 박혀
  있습니다. 재생목록 링크를 비밀번호처럼 다뤄야 하는 이유입니다.
- **살아 있는 연결은 없습니다.** 파일은 가져온 순간의 스냅숏입니다. 이후에
  추가된 채널은 들어 있지 않고, 그것이
  [Xtream Codes API](/ko/blog/xtream-codes-와-m3u-비교/)와의 진짜 차이이자
  [목록이 어디에 사는지가 중요한](/ko/blog/재생목록-주소와-기기-속-파일/) 이유입니다.
- **선언된 문자 체계가 없습니다.** 형식 어디에도 자기 인코딩을 밝히는 자리가
  없고, 바로 그래서 가끔
  [채널 이름이 기호로 도착합니다](/ko/blog/채널-이름이-깨져-보일-때/).

## 자기 목록을 읽어 보기

목록이 이상하게 굴면 열어서 보십시오. 빠진 `#EXTM3U`, 모든 줄에서 비어 있는
`group-title`, 파일 전체에 없는 `tvg-id`, 쉼표가 끼어든 이름 — 각각은
플레이어에서 뚜렷이 다른 흔적을 남기고, 각각은 십 초쯤 읽으면 눈에 들어옵니다.

이 형식은 통째로 머릿속에 담아 둘 만큼 작습니다. 흔치 않은 일이고, 활용할
가치가 있습니다.
