**M3Uファイルとは、テキストで書かれたプレイリストです。**各項目は曲や動画、
ライブ配信の「アドレス」で、たいていその直前に、名前や説明を書いた行が一行
付きます。拡張子の由来は*MP3 URL*、つまり音楽の再生リストという元々の用途に
あります。いまではIPTVの事業者がチャンネル一覧を渡すときの標準的な形式で、
`.m3u8`は同じ形式をUTF-8で保存したものです。

この形式には「技術的で難しい」という評判がありますが、それは不当です。
いまも日常的に使われている形式のなかでは、もっとも単純な部類に入ります。
名前の並び、アドレスの並び、そしていくつかの補足。テキストエディタで開けば
読めますし、一度読んでしまうと、プレイヤーの挙動の多くが「なんとなく変」から
「そういう仕組み」に変わります。（再生したいだけなら、
[M3Uファイルの開き方](/ja/blog/m3u-ファイル-の-開き方/)は別の、もっと短い話です。）

以下は完全に動作するプレイリストです。チャンネル二つ、省略なし。

```
#EXTM3U url-tvg="http://example.com/guide.xml"
#EXTINF:-1 tvg-id="one.example" tvg-name="Channel One" tvg-logo="http://example.com/one.png" group-title="ニュース",チャンネル一
http://example.com/live/one.ts
#EXTINF:-1 tvg-id="two.example" tvg-name="Channel Two" group-title="スポーツ",チャンネル二
http://example.com/live/two.ts
```

形式としてはこれで全部です。以下はこの五行の案内です。

## ヘッダー

```
#EXTM3U
```

最初の行はこの通りでなければならず、その役目は「これから拡張M3Uが続く」と
宣言することだけです。この行がなくても読み込めることはありますが、そのとき
プレイヤーには、次に説明行が来ると期待する根拠がありません。

ヘッダーは、プレイリスト自身が番組表を指し示す場所でもあります。

```
#EXTM3U url-tvg="http://example.com/guide.xml"
```

`url-tvg`（同じ意味の `x-tvg-url` でも構いません）はXMLTVファイル——
[チャンネル一覧とは別の予定表を持つ文書](/ja/blog/epg-番組表-の-仕組み/)——を指し、いま
何が放送されているかを供給します。プレイリストがこれを持っているのに番組表が
出ないなら、少なくとも二つのファイルのどちらを疑うべきかは決まります。

## 説明行

```
#EXTINF:-1 tvg-id="one.example" tvg-name="Channel One" group-title="ニュース",チャンネル一
```

`#EXTINF` は一つの項目の始まりです。三つに分けて読みます。

**数字。** コロンの直後にあるのは秒単位の長さです。生放送では `-1`、つまり
「決まった長さがない」という意味になります。映画なら実際の秒数が入ることも
あります。

**属性。** 任意の `key="value"` の組です。効いてくるのは次のあたり。

- **`tvg-id`** — このチャンネルをXMLTVの番組と結びつける識別子です。番組表は
  読み込めているのに中身が空、という症状のいちばん多い原因がこれです。
  プレイリストと番組表で識別子が食い違い、何も一致しないのです。
- **`tvg-name`** — 番組表と突き合わせるための名前で、画面に出る名前とは必ず
  しも一致しません。
- **`tvg-logo`** — ロゴ画像のURLです。ネットワーク越しに取得される画像が
  チャンネルの数だけあるので、大きな一覧が最初に「揃った顔」になるまで少し
  時間がかかります。
- **`group-title`** — そのチャンネルが入るカテゴリです。プレイヤーで
  スクロールしていくときに通り過ぎる見出しは、すべて事業者がここに一つずつ
  打ち込んだものです。
  [カテゴリを自分で手なずける価値がある](/ja/blog/プレイリスト-の-整理-と-検索/)のは、
  これが理由です。

**表示名。** カンマの後ろ、行末までがそのまま画面に出る名前です。引用符の
ない生のテキストなので、チャンネル名の中のカンマはこの形式の本物の落とし穴に
なります。

## アドレス

```
http://example.com/live/one.ts
```

`#EXTINF` の直後の行に、映像の在処があります。再生時にネットワークに触れる
唯一の行であり、[ストリームの振る舞い](/ja/blog/hls-dash-rtsp-の-違い/)を
決めるのもここです。`.m3u8` のアドレスならセグメントで届くHLS、`.ts` の
アドレスなら連続した伝送ストリームです。

ここから二つ、役に立つ結論が出ます。第一に、説明行だけあってアドレスのない
項目は見えません。再生するものがないからです。第二に、一覧は完璧に開くのに
どのチャンネルも再生できないプレイリストとは、名前は正しくアドレスが死んで
いるプレイリストです。それは
[プレイヤーではなく事業者側の問題](/ja/blog/iptv-プレイヤー-の-役割/)です。

## そこに入っていないもの

入っていないものを知ることも、同じくらい示唆に富みます。

- **映像は入っていない。** 四万チャンネルのプレイリストでも数メガバイトの
  テキストです。そのうち一コマも絵ではありません。
- **ログインは入っていない。** 認証が要る場合、それはたいていアドレス自体に
  埋め込まれています。プレイリストのリンクをパスワードとして扱うべき理由が
  これです。
- **生きた接続は入っていない。** ファイルは取得した瞬間の写しです。あとから
  追加されたチャンネルは含まれません。それが
  [Xtream Codes API](/ja/blog/xtream-codes-と-m3u-の違い/)との本当の違いであり、
  [一覧がどこに置かれているかが効いてくる](/ja/blog/url-の-プレイリスト-と-端末内-の-ファイル/)
  理由でもあります。
- **文字コードの宣言は入っていない。** 形式のどこにも自分の文字コードを述べる
  場所がありません。だからこそ
  [チャンネル名が記号の列になることがある](/ja/blog/チャンネル名-が-文字化け-する-理由/)のです。

## 自分の一覧を読む

挙動がおかしいときは、開いて眺めてみてください。`#EXTM3U` がない、全行の
`group-title` が空、`tvg-id` がどこにもない、名前の中にカンマが紛れている——
それぞれプレイヤー側に固有の症状として現れますし、どれも十秒ほど読めば
目に入ります。

頭のなかに丸ごと収まる大きさの形式です。これは珍しいことで、利用しない手は
ありません。
